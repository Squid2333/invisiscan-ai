# 分阶段实施计划

本文把 [架构设计](ARCHITECTURE.md) 第 10 节展开成可执行的工作包。架构与行为语义以 `ARCHITECTURE.md`、`DATA_MODEL.md` 为准；部署、双库复制和运维细节以 `IMPLEMENTATION_PLAN.md` 为准；DDL 以 `migrations/` 为准。本计划只安排实现与验收，不引入新的算法行为。

当前仓库已有 `proto/invisiscan/v1/`、`migrations/` 和旧链路代码；Go、Python 服务及部署目录尚未实现。以下步骤按这个起点编排，不把已有协议和迁移重新当作空白工作。`legacy/` 保持原样、可运行；权重和回归数据放在 Git 以外。

## 总览与阶段门槛

| 阶段 | 要先具备 | 阶段结束时能证明什么 | 主要难点 |
|---|---|---|---|
| 一：骨架与数据层 | 现有 proto、DDL | 假帧到落库的闭环、双库复制和崩溃恢复可重复测试 | 事务边界、双向复制、状态机 |
| 二：采集与感知 | 一的帧/服务接口和存储 | 实际摄像头的时间可信；感知结果对齐旧链路 | RTCP 时间、GPU 环境、逐帧对齐 |
| 三：跟踪器 | 二的逐帧结果及旧链路黄金数据 | Go BOTSORT 和事件/轨迹语义逐帧回归通过 | LAPJV、Kalman 状态、ID 演化 |
| 四：分类与人脸 | 三的轨迹点、裁剪图和可恢复任务 | 轨迹到识别日志的异步链路可重放、可恢复 | 旧底库迁移、图像差异、幂等 |
| 五：归档与运维 | 二的推流、四的完整业务链路 | 单机部署、回放、预览上传、断网恢复可运行 | 磁盘容量、复制积压、跨项目回放 |
| 六：ReID（可选） | PersonViT 代码、权重及标注样本 | `pending_reid` 能完成身体识别 | 模型契约和阈值尚未知 |

阶段一可以在开发机做；阶段二起需要主机 A、实际摄像头和模型权重。阶段一的双库测试在本机容器内完成，阶段二再接入真实 WireGuard 网络。阶段二和三的感知、跟踪工作可并行准备，但端到端验收依次进行。阶段四的底库迁移脚本可提前开发，正式迁移要等 FaceService 与复制链路可用。

每阶段交付一份简短的验收记录：使用的代码版本、权重哈希、样本来源、运行命令、实测值、与旧链路的差异及处理结论。没有可复现的输入或验收记录，不算阶段完成。

## 阶段一：骨架与数据层

**目标：** 用确定性的假数据证明协议、状态机、事务和复制能工作，不依赖摄像头或 GPU。

1. **固定契约和测试基线。** 核对现有 proto、DDL 与 `DATA_MODEL.md` 的字段和写入方。主要表、任务认领字段、`face_embeddings`、`domain_events`、`pipeline_heartbeats` 已在 `0001_init.sql`；保持其不变，通过后续迁移补充可执行约束。站点脚本按 `migrations/site/README.md` 的顺序运行；`0002_seed.sql` 只在云端执行。建立 `buf lint`、`buf breaking` 和迁移顺序检查。
2. **生成项目骨架。** 建 Go 模块、配置校验、proto 生成、pgx/sqlc、结构化日志与退出流程；Python 起一个按既有 `Perceive` 协议返回固定 `SessionReady`/`FrameResult` 的 mock 服务。设置本机 PostgreSQL、pgvector、两个站点的测试数据库及可重复的启动命令。
3. **先实现数据层。** 用真实 PostgreSQL 测试事件、轨迹、点、图片、识别日志的读写；确认“首条确认轨迹同时创建事件和轨迹”、批量点写入、状态条件更新和 `recognition_logs` 唯一约束。测试主机 A 与云端的写入方边界、双向表 ID 错开和 `origin = none`，包括断连后补同步。

   **状态：已完成（2026-11-27）。** `go/internal/store` 已实现事件/轨迹事务创建、`CopyFrom` 批量写点、图片读写、条件结束轨迹/事件、识别日志幂等写入和读回。真实 PostgreSQL 16 双库集成测试通过：首条轨迹失败时事务回滚；事件、轨迹、点、图片、识别日志读写通过；`(track_id, modality)` 冲突不重复插入；A 与云端 publication 写入边界符合契约；事件依赖行 A→云复制、云端位置/相机配置云→A复制；`subjects` 与 `face_templates` 双向插入使用奇数/偶数 ID 且不回环；禁用订阅期间 A 的记录在恢复后追平。运行命令：`go test ./go/internal/store -count=1`（需设置 `INVISISCAN_TEST_DSN`、`INVISISCAN_CLOUD_TEST_DSN`；双库复制还需 `INVISISCAN_REPLICATION_TEST=1`、`INVISISCAN_A_TEST_DSN`）。
4. **接通假的实时链路。** 用假帧源、mock PerceptionService 和可替换的确定性跟踪桩驱动事件 FSM，验证检测框数开关事件、3 帧确认、20 帧缺席关闭、短轨迹丢弃、事件起止时间回写与轨迹点坐标。跟踪桩只用于本阶段的链路测试，阶段三换成 Go BOTSORT。

   **状态：实现已接入，端到端验收待运行（2026-11-28）。** 基线为 `2c53490`，验收输入由 Go 假帧源和 Python mock 生成，无需录像或权重。固定场景在第 22 帧丢弃仅有两次输出的待确认事件，第 26 帧首次落库，第 28 帧将事件起点从第 24 帧回写到第 23 帧。第 50 帧的低分检测将缺席计数清零，第 70 帧关闭事件，结束时间取第 30 帧。预期结果为 1 条事件、2 条轨迹及 8 个点。运行命令、数据库查询和集成测试见[本地开发环境](../deploy/dev/README.md)。

5. **接通恢复路径。** 在写点、确认和关闭处模拟进程中断；重启后只 reconcile 当前实例持有的相机，已确认轨迹能结束并进入待处理状态，重复启动不生成重复事件。相机归属的 advisory lock 与限定相机的 reconcile 在这一阶段设计并测试，避免阶段三接入真实相机后出现全表关单。

**验收：** testcontainers 起真实 PostgreSQL 的集成测试通过；两站点复制测试证明 A 写的事件/轨迹到云、云端相机配置到 A、双向模板插入无冲突；固定假帧可得到可查询的事件、轨迹和点；逐个中断点重启后状态收敛且没有重复记录。

**难点与问题：** 轨迹点批量写入与“轨迹结束时查全部点”之间必须有刷盘屏障，否则分类读到不完整序列。双库复制不同步 DDL，也不会替应用兜底跨站点写入冲突；先用本机双库测试检验迁移顺序和外键关联。真实 WAL 日增长量此时只能开始测，容量阈值等有连续数据后再定。

## 阶段二：采集、帧时间与感知服务

**目标：** 让实际相机稳定地产生带可信时间的帧，并让 Python 感知服务输出与旧链路一致的检测输入。

1. **核实设备与推流。** 在 A 上记录 `v4l2-ctl --list-formats-ext` 结果，确认 MJPEG/分辨率/8 fps；用 `transpose=2` 验证方向，配置 MediaMTX `runOnInit` 与重启。记录实际码率、CPU/GPU 占用和录制目录增长，核算 4 天保留期的磁盘余量。此时可打开 MediaMTX 录制用于容量测试，切片登记放到阶段五。
2. **实现拉流与帧时间。** gortsplib 接收 RTP/RTCP，解码 H.264，给帧保留 RTP 序号、时间戳和 `clock_source`；在第一个 SR 前缓存待定帧或丢弃，按选定策略做回放测试。SR 长时间缺失才进入 `fallback_local` 并告警。用同一台主机的采集侧记录对照 MediaMTX 时间，实测偏移与 SR 间隔；确认时钟同步和重连后的时间单调性。
3. **实现调度与传输。** 单槽最新帧、单流仅一个在途 `Perceive` 请求；校验丢帧计数与帧序号连续性口径。Go 客户端同时支持 Unix socket 和本机 TCP 地址，Python 按现有 proto 返回有效配置、模型标识和逐帧时间；测 16 MB 消息限制、两种地址的吞吐及延迟，并实测单 GPU 在目标延迟下能承载的相机路数。
4. **移植感知链路。** 锁定 Python 环境和权重哈希，按旧链路顺序实现缩放、VideoDepthAnything 时序窗口、YOLO26m-seg、ROI 深度门限、深度过滤、depth-aware NMS、每框深度、检测模型 ReID 特征、`sparseOptFlow` GMC。每个中间量都能写入离线对比结果，不改变算法阈值。
5. **建立同帧回归。** 使用同一段原始录像分别喂给旧链路和新服务，按输入帧编号而不是处理完成时间配对；分别比较缩放尺寸、检测框与顺序、分数、深度门限、过滤后框、ReID 特征和 GMC。记录 GPU/库版本和浮点误差，先定位第一处差异，再看最终输出。测试空画面、多人、遮挡、ROI 无有效深度和流断开重连。
6. **接入真实站点网络。** 在 A 与云端建立由 A 主动连接的 WireGuard 隧道，验证 PostgreSQL 双向订阅能在实际网络下初始同步、断线重连和继续追赶；A 的时钟同步与隧道端口限制按 `IMPLEMENTATION_PLAN.md` 第 4 节检查。

**验收：** 实际相机可持续推流和解码；时间偏移、SR 到达间隔、缺失比例及码率有实测记录；同帧回归的每一项差异都有数值与归因，达到本阶段事先固定的容差；最新帧调度不会在推理慢时持续积压。

**难点与问题：** SR 首次到达前的帧如何处理尚有两种设计，需在开发前选一种并写入配置/测试；时间源在 MediaMTX 接收侧，需确认实际偏移能满足业务要求。VDA 和 GMC 有跨帧状态，离线回归必须用相同的帧序列与重置点；一旦新链路丢帧，应另测“丢帧后状态”，不能拿它与旧链路逐帧结果直接比较。

## 阶段三：Go BOTSORT 与事件/轨迹回归

**目标：** 用同一组跟踪输入逐帧验证 Go 移植，随后替换阶段一的跟踪桩。

1. **制作黄金数据。** 在 `legacy/` 以外建立临时可运行副本，用独立录制工具在 `tracker.update` 边界采集 JSONL：帧号、检测框及顺序、分数、ReID 特征、GMC 矩阵、输出轨迹行和 removed 集合。黄金数据和权重留在 `testdata/` 或外部存储，不提交大型样本；记录旧 ultralytics/lap 版本及样本哈希。原仓库的旧链路保持原样。
2. **拆开纯数学单元。** 依旧版语义实现 Kalman `XYWH`、GMC 应用、IoU/外观距离、`fuse_score`、LAPJV、轨迹状态转移和去重；先用少量手工输入锁住阈值边界、空集和矩阵布局，再做完整回放。`frame_rate = 15`、`max_time_lost = 9`，不按实际 8 fps 改写。
3. **逐帧回放定位。** 每帧比较输出轨迹 ID、激活状态、平滑框（容差 `1e-3` 像素）和 removed 集合；差异从关联代价矩阵和第一次分叉帧查起。相等代价导致的 LAPJV 差异只在能展示相等代价输入和两种合法分配时豁免，并单独登记。
4. **接回实时 FSM。** 替换阶段一的跟踪桩；验证检测框数决定事件开关，0.05～0.1 分的框只影响事件、未激活轨迹不输出、确认轨迹的第一输出时间、深度 EMA、原分辨率裁剪与事件末端截断。测试多人交叉、短暂遮挡、超过 9 帧的丢失、1～2 帧误检及跨事件轨迹。
5. **回归恢复与资源。** 在真实跟踪过程中重启 pipeline，确认相机锁释放/重获、只恢复归属相机、截断轨迹标记 `recovered`；量测 BGR 传输、解码、跟踪、裁剪和写库的逐段耗时。

**验收：** 黄金数据的纯 Go 回放进入 CI 且无需 GPU；除有证据的等代价分配外，逐帧 ID、框和 removed 一致；端到端事件、轨迹、点的状态与旧口径一致；重启后没有悬挂的 `open` 事件和 `confirmed` 轨迹。

**难点与问题：** 最容易产生级联偏差的是关联次序、LAPJV 等代价选择、Kalman 数值状态和新轨迹激活时机；必须比较第一处分叉，不能只比较最终轨迹总数。阶段二的输入差异会污染此验收，纯跟踪回放必须固定旧链路输入。

## 阶段四：轨迹分类与人脸识别

**目标：** 完成“轨迹结束 → 分类 → 分割 → 人脸识别/陌生人注册”，并能安全重试。

1. **接通任务认领。** `tracks` 上按 `next_attempt_at`、`locked_until` 做 `SKIP LOCKED` 租约，channel 只负责唤醒；任务失败按约定退避，到上限进入 `failed`。先验证同一轨迹由两个 worker 竞争、租约过期重领和进程重启续做。
2. **移植分类与分割。** PerceptionService 增加 LSTM `ClassifyTrajectory` 与 yolo11m-seg `SegmentBodies`；从 `track_points` 重建旧 txt 的坐标和深度语义，按旧阈值处理少于 5 点、预处理不足 15 步和低于 0.3 的结果。全部类别都做分割；图像按稳定对象键写入，状态推进在产物完成之后。
3. **构建 FaceService 与底库计算。** 锁定独立 Python/torch 环境，接通 MTCNN、AdaFace、DSL-FIQA；A 轮询新模板并写 `face_embeddings`，失败记录原因和次数。按 `DATA_MODEL.md` 的脚本流程迁移旧 `pictures` BLOB，先做小样本核验，再执行可重复的正式导入。
4. **实现识别判定。** Go 按旧 `compute_user` 规则对所有 ready 模板打分；按 `0.35`/`0.349` 两轮阈值、质量优选与 `0.15` 入库下限决定 matched、enrolled、unmatched 或 no_face。自动注册 subject/template/embedding、识别日志和领域事件在一个事务中写入；靠唯一约束保证重试不重复注册。Fay 通知不在本阶段实现。
5. **回放与故障测试。** 用已有轨迹目录和旧识别记录回放，分类、人脸对齐、特征、得分、最终身份分别比；包含没有人脸、提特征失败、低质量陌生人、多个模板和身份合并/停用。对分割写完、状态更新前和注册事务提交前后分别中断，检查重放结果。

**验收：** `DATA_MODEL.md` 的旧图抽样特征相似度 `> 0.9999`，5 条已识别轨迹命中同一人且分数差 `< 1e-4`；分类和判定差异逐例记录并定位；重复投递只留一条 `(track_id, modality)` 日志；无法处理的轨迹进入可查询的 `failed`，不会静默丢失。

**难点与问题：** Go JPEG 编码与旧 `cv2.imwrite` 不逐字节相同，可能影响分割、人脸对齐和最终得分；回归时要同时保留旧 body 图与新裁剪图，区分编码差异和算法差异。正式迁移依赖旧 MySQL 可读、云对象存储可写和 A→云复制正常；需要先确认旧库访问与图片总量。

## 阶段五：归档、预览与运维交付

**目标：** 把阶段二已有的录制接入元数据和回放，把完整链路变成可部署、可观察、可恢复的服务。

1. **登记与校验录像。** MediaMTX 完成切片时调用本机 `POST /internal/recordings`，校验 token、路径和时长，按对象键幂等登记；启动时扫描录制目录补登漏掉的切片。对照实际文件核对起止时间、大小和删除时间；4 天过期后元数据保留且能显示不可回放。
2. **完成图片交付。** 非 `discarded` 轨迹按时间等分选最多 10 张 body 图，压缩至长边 512、质量 75 上传 S3，成功后写 `preview_key`/`uploaded_at`；自动注册的模板原图也上传。断网时保留待上传任务，重连补发；云端只展示上传成功的图。
3. **补齐部署与观测。** `docker-compose`/systemd 拉起本地 PostgreSQL、MediaMTX、pipeline、两个 Python 服务、Vector 和 Prometheus；加入健康检查、GPU/模型权重校验、结构化日志、心跳、领域事件和指标。指标至少覆盖帧率、丢帧、SR 缺失、推理延迟、任务积压/失败、识别命中、磁盘、复制延迟与复制槽 WAL。
4. **验收网络与保留策略。** WireGuard 仅在隧道地址暴露复制和回放端口；invisiscan-main 经隧道代理 HLS/playback，并按云端 `recordings` 与 `events` 查回放时间段。模拟断网和重连，检查业务仍写 A 本地库、复制自动追赶、上传和 Vector 缓冲补发；按实测 WAL/日志日增长量设置 5 天容量，检查告警。云端恢复演练及 A 重建按 `IMPLEMENTATION_PLAN.md` 第 5 节执行。
5. **交付运行手册。** 记录启动/升级顺序、双站点先扩展后收缩迁移、恢复订阅、确认录像过期、重试失败轨迹、查看本地指标与磁盘清理的操作。`ops_commands` 只定后续表契约，不在此阶段实现执行器。

**验收：** 从空机按手册启动后能完成实际“采集 → 识别 → 云端查询/预览/回放”；停掉切片回调后重启能补登且不重复；断网期间本地业务不中断，恢复后复制及上传追平；至少一次按手册完成云端恢复与 A 重建演练。

**难点与问题：** 4 天录像保留短于 5 天断网容忍，断网首日录像可能在恢复前过期，这属于当前产品约束。实际码率、图片量、WAL 和 Vector 日志量决定磁盘需求；阶段二和本阶段都要用实测值更新容量表。invisiscan-main 的代理和页面属于另一个项目，联调时需确定对应版本与负责人。

## 阶段六（可选）：ReID 接入

取得 PersonViT 代码、权重、输入预处理和可标注的出门轨迹后，先固定 embedding 维度、归一化、相似度方向、质量分和阈值；据此完成 `ReIDService`、`body_templates` 的迁移及写入方/复制配置。用历史 `pending_reid` 轨迹回放验证提特征、匹配、识别日志幂等和 reconcile 补投，再开启实时处理。没有模型或可靠阈值前保持 `reid.enabled = false`，outdoor 轨迹停在 `pending_reid`，不假定其身份。

阶段六验收需有已标注的同人/异人轨迹集和误识率目标；这些输入目前未具备，不能用“服务能返回向量”代替业务验收。模型升级和 ONNX/TensorRT 加速属于 `IMPLEMENTATION_PLAN.md` 第 6 节的可选阶段七，应在二到四的等价基线通过后单独评测。

## 需提前定下的问题

| 截止阶段 | 问题 | 建议的决策或所需证据 | 不解决的影响 |
|---|---|---|---|
| 一 | 现有 DDL、proto 与文档是否还有字段偏差 | 逐表/逐消息核对并追加迁移；以 `migrations/` 为 DDL 来源 | 后续代码按不同契约实现 |
| 二 | 首个 RTCP SR 前缓存还是丢帧、何时启用 fallback | 用启动与断流样本测 SR 间隔后固定策略、超时和告警值 | 帧时间口径不稳定，回归无法配对 |
| 二 | 感知浮点误差和性能通过线 | 固定录像、版本、权重哈希，先记录旧链路重复运行波动，再设各中间量容差和端到端延迟目标 | “一致”无法客观判定 |
| 二/五 | 4 天录像与 5 天断网所需磁盘是否足够 | 实测码率、图片、WAL、日志增量，连同安全余量形成容量表 | 磁盘耗尽会同时影响录像与数据库 |
| 三 | LAPJV 相等代价造成的 ID 差异如何审批 | 保存第一处分叉的代价矩阵，逐例登记豁免 | 难以分辨合法差异与移植错误 |
| 四 | 旧底库与轨迹样本能否稳定读取 | 确认 MySQL 访问、图片数量和旧链路回放样本，先做 20 图/5 轨迹试验 | 无法验证迁移后的识别一致性 |
| 四 | JPEG 编码差异的接受范围 | 用同一张旧 body 图分别跑两条服务路径，单独统计对齐/得分偏差 | 图像差异会被误判为模型移植问题 |
| 五 | invisiscan-main 的回放代理和预览接口何时联调 | 按 `ADMIN_API.md` 固定跨项目版本、样本及责任人 | A 侧完成后仍无法端到端验收 |

阶段门槛未通过时保留该阶段的输入和差异记录，先修正根因再推进依赖它的验收。任何想改变旧链路算法口径的工作单独进入阶段七，避免把架构迁移和算法调整混在一次回归中。
